# Repository collaboration

## Implementation plan and behavior specification

Desktop owns the WhatsApp collaboration bridge. A group links multiple explicitly selected repositories, with exact participant-to-repository grants. Groups start paused. The owner enables a group after configuring access. Participants issue explicit `Forger, Backend: ...` instructions; ordinary conversation has no effect. Ambiguous repository selection produces help. An instruction can select multiple aliases separated by `+`, and requires permission to every selected repository.

Implementation proceeds through shared DTOs and normalized SQLite persistence, deterministic commands and permission checks, then transport/executor integration and the Connections interface. The transport verifies stable sender identities; names do not authorize. Only live messages newer than group activation are eligible. Deduplication includes connection, group, message, and sender identity. The executor receives only the authorized repository roots and its own restrictive runtime configuration. A message is bounded to 12,000 characters and each group accepts at most 100 queued turns.

Behavior checks precede implementation: unauthorized names and unknown LIDs do not execute; from-account verified messages work; history and automated messages do not execute; duplicate incoming messages execute once; ambiguous aliases prompt clarification; all roots in a multi-repository task need grants; overlapping roots serialize; revocation cancels queued work and aborts running work; continuation checks all permissions again; restart marks interrupted work for owner attention without replay; failed outgoing delivery retries independently of execution.

## Operating contract

The owner selects existing normal Git checkouts from the native Desktop folder chooser. Each checkout keeps its own real `.git` directory. Symbolic repository roots, worktrees or submodules with external Git metadata, the filesystem root, and the home directory are rejected during configuration. Public DTOs omit their paths. Repository aliases are unique within a group and cannot contain command separators. Group members never gain access merely by being present in the conversation. Participant identities originate in the live transport roster and are compared exactly, including their identity namespace.

Examples: `Forger, Backend: agrega un filtro`, `Forger, Backend + Desktop: actualiza el formulario`, `Forger, estado #<tarea>`, `Forger, cancelar #<tarea>`, and `Forger, #<tarea> permite elegir varios`. A reply to a Forger task message, still explicitly addressed to Forger, can continue that task. Continuations are queued as separate attributable turns with the same Codex conversation; each turn retains its author and requested repository set. Active or queued turns accept additional instructions as dependent turns. Those turns begin only after their predecessor completes successfully. A failed, cancelled, or interrupted predecessor blocks continuation for local review. Task replies show an eight-character reference, scoped uniquely to that group. Repositories in one instruction are selected explicitly; a single authorized repository can be inferred. Commands and responses support Spanish and English.

The normalized database stores groups, repositories, participants, grants, incoming message receipts, tasks, task repository associations, and outgoing messages. Durable outgoing delivery cannot promise exactly-once delivery if WhatsApp accepts a send but the process exits before recording the receipt. It never reruns Codex to repair delivery. Running tasks interrupted by restart require an explicit owner retry; such retry starts a fresh conversation because the prior runtime state is ambiguous.

The queue locks canonical repository paths, including ancestor/descendant overlap, across groups. Permission is checked at acceptance, execution, continuation, and outgoing delivery, including after the outgoing transport throttle. Current group membership is revalidated. Results are only shared in the group if every current human recipient has access to every selected repository; otherwise the group gets a generic local-review notice. Group pause and grant removal suppress pending results, cancel pending tasks, and signal abortion for active runs. Abortion cannot undo edits already completed by Codex. Removing a repository only unlinks configuration; it never deletes local files.

## Runtime support and limits

Execution supports macOS and requires the authenticated Codex runtime managed by Forger. The executor checks the exact version declared by `CODEX_CLI_VERSION` and applies a strict explicit permissions profile; incompatible runtimes fail closed. A selected checkout is readable and writable for code changes, but its Git metadata is read-only, so the task does not create commits. Worktrees or submodules whose Git metadata resides elsewhere are unsupported. The executor accepts at most ten explicitly selected repository roots in a task.

Collaboration owns isolated Codex conversations that are separate from, and are not displayed as existing chats in, the Codex desktop application. Command network access and Codex web search are disabled. Codex itself still communicates with its model provider to process the task. MCP integrations, plugins, hooks, additional agents, and inherited user rules are disabled for this execution scope. Publication and deployment are outside the allowed workflow.

Repository access includes files inside the selected repository, potentially including `.env` or other sensitive files stored there. The feature does not claim to identify or exclude every secret inside a granted repository. Access to other personal folders and the isolated Codex credential directory is denied to executed commands. Repository instructions are untrusted inputs and cannot expand the runtime permissions.

Desktop remains running for queue execution. When WhatsApp is disconnected, previously accepted queued tasks wait until current group membership can be verified again. Interrupted running work requires local review; it is not replayed automatically. Terminal task prompts/results persist locally and are not platform memory.
